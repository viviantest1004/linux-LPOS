WHAT THIS IS
------------
A Linux distribution written from nothing: its own C library, its
own init, its own shell, its own bootloader, and 130
commands. No busybox, no glibc underneath it, no userland from
anywhere else.

The whole system is one kernel image file, 13-22MB, unpacked into
RAM at boot. Nothing on disk is part of the running system, so
pulling the power leaves nothing to corrupt: the next boot is
always the factory state. What you install is kept separately, on
the data partition, and comes back on top.

It began on a Raspberry Pi Zero 2 W, which has 512MB of RAM that
Ubuntu spends half of before you have done anything. Nothing in it
turned out to be specific to that board, so it now runs on arm64
virtual machines and ordinary amd64 PCs as well.


WHO WROTE IT
------------
Claude Code, Anthropic's coding agent, working from the repository
owner's direction. All of it: the kernel configuration, the C
library, init, the shell, every command, the bare-metal bootloader,
the build system, the self-test, and this file.

The design and the debugging are on the record - each commit
explains what was wrong and why the fix is shaped the way it is,
and the comments say what was tried and what broke. Nobody
independent has reviewed any of it.


BEFORE YOU RELY ON THIS
-----------------------
None of this is "so do not use it". It is all "so do not be
surprised".

  * A hobby operating system, not a supported product. No security
    team, no CVE process, nobody on call. For anything that has to
    keep working, use Raspberry Pi OS Lite or Debian.

  * Real Raspberry Pi hardware is not verified. Everything was
    tested in QEMU. WiFi association, the thermal sensors, the
    hardware watchdog and the EMMC driver against an actual card
    are all unconfirmed.

  * The security work has not been audited by anybody outside the
    repository. Signature checking on updates, the firewall, the
    DNS and NTP spoofing defences are all implemented and the
    reasoning is in the comments, and that is not the same thing.

  * The C library is ours and it is not complete. It has what the
    commands need. Compiling something else against it can run into
    a function that is not there. Ordinary Linux binaries run
    anyway, on the glibc that ships beside Python.

  * /data is the only thing that survives a reboot, and it is one
    partition on one card. Cards die. Back up what you care about.

  * dd to the wrong device destroys that device. Check /dev/sdX
    twice. It is the one mistake here a reboot cannot undo.

  * No GUI, and it does not run containers. The DRM drivers are in
    the kernel but X11 or Wayland is yours to install, and cgroups
    and namespaces are not enabled for container use.

  * There are rough edges, and they are usually of the quiet kind.
    Recent ones: `echo x | grep x` answered "command not found" for
    as long as the shell had existed, because a pipeline forked and
    exec'd every stage and echo is a builtin; `cmd ; echo $?` was
    always 0; apt could never have worked, because the Debian base
    image ships /etc/resolv.conf as a symlink into /run and writing
    over it failed unnoticed. All three are fixed and each has a
    check in the self-test now. Expect more of the same.

What IS verified, on real QEMU boots of both architectures: the
self-test passes with nothing failing. Separately: a fork bomb is
cleared in a single sweep with init, SSH and the log still running;
memory exhaustion kills the process that caused it and nothing
else; apt fetches, installs and runs a Debian package.


WHICH IMAGE DO I WANT
---------------------
  dist/test_a_123_LPzero2W_linux.img.xz
      Raspberry Pi Zero 2 W hardware AND arm64 virtual machines.
      One image does both: it carries an uncompressed kernel for
      the Pi's GPU and an EFI executable for UEFI.

  dist/linux-LP_amd64.img.xz
      Ordinary PCs and desktop VMs - VMware, VirtualBox, QEMU/KVM,
      Hyper-V. It calls itself linux-LP from the inside, because it
      is not a Raspberry Pi and should not say it is.

  dist/test_a_123_LPzero2W_linux-utm.zip
      A ready-made UTM bundle for arm64 VMs. Unzip, double-click.
      No GPU firmware, so it will not boot on the board.

Check what you downloaded before you use it. A truncated image
fails in confusing ways halfway through boot:

      sha256sum -c dist/SHA256SUMS.txt


ON A RASPBERRY PI ZERO 2 W
--------------------------
      xz -d < test_a_123_LPzero2W_linux.img.xz \
        | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress

Check /dev/sdX. Get it wrong and that disk is gone.

On the first boot the data partition grows to fill the card by
itself. Put it in, power it on, and the serial console is on GPIO
14 and 15 at 115200 - or plug in a monitor, there is a shell there
too.


IN A VIRTUAL MACHINE
--------------------
Decompress, attach as a disk, and set UEFI boot. The MBR
bootstrap is deliberately empty, so legacy BIOS will not start it.

  QEMU, arm64:
      qemu-system-aarch64 -M virt -cpu cortex-a72 -m 4096 -smp 4 \
        -drive if=pflash,format=raw,readonly=on,\
file=/usr/share/AAVMF/AAVMF_CODE.fd \
        -drive if=pflash,format=raw,file=vars.fd \
        -drive file=test_a_123_LPzero2W_linux.img,format=raw,if=virtio \
        -netdev user,id=n0,hostfwd=tcp::2222-:22 \
        -device virtio-net-pci,netdev=n0

  QEMU, amd64:
      qemu-system-x86_64 -m 4096 -smp 4 \
        -drive if=pflash,format=raw,readonly=on,\
file=/usr/share/OVMF/OVMF_CODE_4M.fd \
        -drive if=pflash,format=raw,file=vars.fd \
        -drive file=linux-LP_amd64.img,format=raw,if=virtio

For a bigger disk, truncate -s 16G the image file. It is sparse,
so it only takes the space it uses, and /data grows into it on the
next boot.


GETTING IN OVER SSH
-------------------
The SSH server is there from the start and comes up on its own.
Password authentication is not compiled into it at all - on a board
facing the internet a password is a matter of time, so it was not
offered as an option.

That used to mean a freshly burned card let nobody in, and the only
way to add a key was a card reader. Now:

      authkey new

generates a keypair on the machine, authorises the public half,
leaves the private half where you can fetch it, and prints the
exact command to connect with the machine's real address in it.

If you would rather use a key you already have, the first partition
of the card is FAT32 and opens on any computer:

      cat ~/.ssh/id_ed25519.pub >> /media/BOOT/authorized_keys

While /boot/authorized_keys exists it is the source of truth, and
editing the copy on the machine is overwritten at boot. Delete it
from /boot to manage keys on the machine instead. It works this way
so that even if /data is destroyed, pulling the card puts a key
back.

Find the address with `ifconfig` or `info net`. There is one user,
root. In a VM, forward the port and connect to localhost:2222.

When it does not work:

      authkey -l              which keys are authorized
      service status dropbear
      firewall status
      netstat -l              is anything listening
      logd                    login records in /data/log/auth


WHAT IT CAN DO
--------------
      help                    every command, grouped
      help <name>             one of them
      info                    everything about this machine
      info -s                 the short version

  Text and scripting
      sed awk grep diff sort uniq cut tr printf xargs head tail wc
      nl rev cmp seq find tee cat more edit

      grep is POSIX: + and ? are ordinary characters, -E gives the
      extended syntax, -F searches for a plain string. grep, sed
      and awk share one engine, so a pattern means the same thing
      in all three.

  The shell
      Pipes, redirection including 2> and 2>&1, && and ||, if,
      while, for, break, continue, functions, $(...) and backticks,
      variables, globs, background jobs, read, shift, export.

      A profile is read at login: /etc/profile, then ~/.profile.
      /root is on the data partition, so ~/.profile survives a
      reboot - that is where your settings go.

  Storage
      disk part datadisk expandfs fsck storage automount dd df du

      Plug a USB drive in and it mounts itself under /media. To
      keep one in the same place across reboots, adopt it:
          storage adopt /dev/sdb photos
      Adopted drives are found by filesystem label, not device
      name, so they come back through a different port.

  Network and serving
      net dhcp ifconfig route ping nslookup wget netstat firewall
      httpd wpa_supplicant

      httpd serves a directory over HTTP. It is not on by default -
      a web server running on every board is not a default anybody
      asked for:
          service add httpd -d /data/www -p 8080
          firewall allow 8080
      `service add` means init supervises it: restarted when it
      dies, still there after a reboot, and guard will not kill it
      under memory pressure.

      Opening a port no longer needs a card reader:
          firewall allow 8080     firewall deny 8080
          firewall ports          what is open, and why

  Packages
      pkg     small packages built for this system, straight onto
              /data
      apt     real Debian packages, into a separate tree under
              /data/debian. The first run downloads 95MB and
              unpacks 440MB, so it is not in the image. Nothing it
              installs can break this system's own commands,
              because they are not in there, and rm -rf
              /data/debian undoes all of it.
          apt install ripgrep
          apt run rg --version

  Python
      CPython 3.12 with pip, and glibc beside it so wheels with C
      extensions work. Ordinary Linux binaries run on that same
      glibc, with or without the `run` wrapper.

  Keeping it alive
      guard watchdog bootcount service integrity defend logd top ps

      guard watches memory, temperature, voltage, CPU and disk. A
      fork bomb is cleared in one sweep. Memory exhaustion kills
      the process that caused it and never init, the shell, SSH or
      the watchdog. init restarts anything in the service list, and
      five boots that fail to last five minutes skip
      /data/rc.local so a bad script cannot lock you out.


WHAT SURVIVES A REBOOT
----------------------
      /data                       kept
      /root                       kept (it is /data/root)
      /bin /lib /usr /opt /sbin   kept (an overlay onto /data), so
                                  cp mytool /bin/ is still there
      /mnt/<adopted drive>        kept, found again by label
      /media/<automounted>        temporary, gone when unplugged
      /etc /tmp /var              gone, deliberately

/etc is rebuilt from the kernel image at every boot because
/etc/rc and /etc/services are read before /data is even mounted,
and a stale copy of either shadowing a system update is how a board
stops booting. Individual files can still be kept:

      persist etc keep /etc/hosts
      persist etc                 what is being kept


BUILDING IT YOURSELF
--------------------
      sudo apt install clang lld llvm gcc-aarch64-linux-gnu \
           mtools dosfstools e2fsprogs xz-utils zip cpio bc \
           bsdextrautils qemu-system-arm qemu-system-x86 python3

arm64 is cross-compiled from an x86 host; amd64 is native.

  arm64:
      ./tools/fetch-kernel.sh
      ./tools/fetch-blobs.sh
      make
      make kernel
      make sdcard-linux

  amd64:
      make ARCH=amd64
      ( cd userland && LP_ARCH=amd64 LP_BINDIR=bin-amd64 \
          LP_ROOTFS_DIR=rootfs-amd64 \
          LP_CPIO_NAME=initramfs-amd64.cpio.gz \
          LP_HOSTNAME=linux-lp LP_OS_NAME=linux-LP ./mkrootfs.sh )
      LP_ARCH=amd64 LP_ROOTFS_DIR=rootfs-amd64 ./kernel/build.sh
      LP_ARCH=amd64 LP_ROOTFS_DIR=rootfs-amd64 \
          ./tools/mksdcard.sh --linux --uefi-only

  All three releases at once:
      ./tools/mkdist.sh

The checksums and the download page are generated from the actual
files by that script. Written by hand they go stale on the first
rebuild somebody forgets, and a checksum that does not match is
worse than none - the person downloading cannot tell a corrupt
transfer from a stale page.

mkrootfs refuses to build an image containing a binary older than
its source. That shipped once: a file was fixed, only one
architecture was rebuilt, and the self-test then failed on code
that was already correct.


CHECKING A BUILD
----------------
      ./tests/selftest.sh

Run it on the machine. Every check prints one line beginning PASS,
FAIL or SKIP, so the result can be read out of a serial log by
something that knows nothing else about this system. SKIP means the
check could not run here and says why - "no watchdog in a virtual
machine" is a fact about the test machine, not a defect.

It is not a formality. Most of the faults listed under BEFORE YOU
RELY ON THIS were found by adding a check for something that turned
out not to work.


WHERE THE SOURCE IS
-------------------
      userland/       one set of sources for both architectures
        libc/         our libc, straight on top of syscalls
        <name>/       one directory per command
      firmware/       the bare-metal bootloader
      kernel/         kernel configuration and build scripts
      boot/           what goes on the boot partition
      tools/          image building, signing, the download page
      tests/          the self-test
      GUIDE/          this file and BRANCHES.txt
      dist/           finished images

There is no arm64/ or amd64/ directory, because both architectures
use the same sources. Exactly three things differ: the syscall
numbers, the entry point in crt0.S, and the kernel configuration.
Splitting them into copies invites fixing one side and not the
other, which has happened here twice.

MIT licensed. The bundled third-party software keeps its own
licences: dropbear (MIT), wpa_supplicant (BSD), OpenSSL (Apache
2.0), the Broadcom GPU firmware (proprietary, redistribution
permitted), and the Linux kernel (GPL-2.0).

이게 뭔가
---------
아무것도 없는 데서 쓴 리눅스 배포판입니다. C 라이브러리도, init
도, 셸도, 부트로더도 자체 구현이고 명령어가 130개입니다.
busybox 도, 그 아래의 glibc 도, 다른 데서 가져온 유저랜드도
없습니다.

시스템 전체가 커널 이미지 파일 하나, 13~22MB 이고 부팅할 때 램으로
풀립니다. 디스크 위의 어떤 것도 돌아가는 시스템의 일부가 아니라서
전원을 갑자기 뽑아도 깨질 데가 없습니다 — 다음 부팅은 항상 공장
초기 상태입니다. 설치한 것은 데이터 파티션에 따로 남았다가 그 위에
다시 얹힙니다.

시작은 라즈베리파이 제로 2 W 였습니다. 램이 512MB 인데 우분투를
올리면 아무것도 하기 전에 절반이 사라집니다. 만들다 보니 그 보드에만
매인 구석이 없어서 지금은 arm64 가상머신과 일반 amd64 PC 에서도
그대로 돕니다.


누가 썼나
---------
Anthropic 의 코딩 에이전트인 Claude Code 가 저장소 주인의 지시를
받아 전부 썼습니다. 커널 설정, C 라이브러리, init, 셸, 모든 명령어,
베어메탈 부트로더, 빌드 시스템, 셀프테스트, 그리고 이 파일까지.

설계와 디버깅은 기록으로 남아 있습니다 — 커밋마다 무엇이 잘못돼
있었고 왜 그 모양으로 고쳤는지가 적혀 있고, 주석에는 무엇을
시도했고 무엇이 깨졌는지가 있습니다. 그것을 독립적으로 검토한
사람은 없습니다.


믿고 쓰기 전에
--------------
여기 있는 어느 것도 "그러니 쓰지 마세요"가 아닙니다. 전부 "그러니
놀라지 마세요"입니다.

  * 지원되는 제품이 아니라 취미로 만든 운영체제입니다. 보안팀도,
    CVE 절차도, 대기하는 사람도 없습니다. 계속 돌아가야만 하는
    일에는 Raspberry Pi OS Lite 나 데비안을 쓰세요.

  * 라즈베리파이 실물에서는 검증하지 못했습니다. 전부 QEMU 에서
    시험했습니다. WiFi 연결, 온도 센서, 하드웨어 워치독, 실제 카드
    위에서의 EMMC 드라이버는 확인되지 않았습니다.

  * 보안 부분은 이 저장소 밖의 누구에게도 감사받지 않았습니다.
    업데이트 서명 검증, 방화벽, DNS·NTP 위조 방지는 전부 구현돼
    있고 근거도 주석에 적혀 있지만, 그것과 검토받은 것은 다릅니다.

  * C 라이브러리가 자체 구현이고 완전하지 않습니다. 명령어들에
    필요한 만큼 있습니다. 그 밖의 것을 이걸로 컴파일하면 없는
    함수를 만날 수 있습니다. 일반 리눅스 바이너리는 파이썬과 함께
    들어 있는 glibc 위에서 그대로 돕니다.

  * 재부팅을 넘겨 남는 곳은 /data 하나뿐이고, 그건 카드 한 장의
    파티션 하나입니다. 카드는 죽습니다. 아까운 것은 따로
    받아두세요.

  * dd 를 엉뚱한 장치에 하면 그 장치가 사라집니다. /dev/sdX 를 두
    번 확인하세요. 여기서 재부팅으로 되돌릴 수 없는 실수는
    이것뿐입니다.

  * GUI 가 없고 컨테이너를 돌리지 않습니다. DRM 드라이버는 커널에
    있지만 X11 이나 Wayland 는 직접 올려야 하고, cgroup 과
    네임스페이스는 컨테이너 용도로 켜두지 않았습니다.

  * 거친 구석이 남아 있고, 보통 조용한 쪽입니다. 최근 것들:
    `echo x | grep x` 가 셸이 존재한 내내 "command not found"
    였습니다 — 파이프의 각 단계를 fork 해서 exec 하는데 echo 는
    내장 명령이라 실행할 파일이 없습니다. `cmd ; echo $?` 는 항상
    0이었습니다. apt 는 애초에 동작할 수 없었습니다 — 데비안 베이스
    이미지가 /etc/resolv.conf 를 /run 안쪽 심볼릭 링크로 넣어두는데,
    그 위에 쓰는 것이 조용히 실패했기 때문입니다. 셋 다 고쳤고
    각각 셀프테스트에 검사가 생겼습니다. 이런 것이 더 나올 거라고
    보시는 편이 맞습니다.

확인된 것은 이렇습니다. 두 아키텍처의 실제 QEMU 부팅에서
셀프테스트가 실패 없이 통과합니다. 따로: 포크 폭탄이 한 번의
패스로 정리되고 init, SSH, 로그가 살아 있으며, 메모리 고갈은 원인이
된 프로세스만 죽이고, apt 가 데비안 패키지를 받아 설치하고
실행합니다.

라즈베리파이 제로 2 W 에서
--------------------------
      xz -d < test_a_123_LPzero2W_linux.img.xz \
        | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress

/dev/sdX 를 꼭 확인하세요. 틀리면 그 디스크가 사라집니다.

첫 부팅에서 데이터 파티션이 카드 전체로 알아서 늘어납니다. 꽂고
전원을 넣으면 됩니다. 시리얼 콘솔은 GPIO 14, 15 에 115200 이고,
모니터를 꽂아도 거기에 셸이 있습니다.


가상머신에서
------------
압축을 풀고 디스크로 붙인 뒤 UEFI 부팅으로 설정하세요. MBR
부트스트랩은 일부러 비워두었기 때문에 legacy BIOS 로는 뜨지
않습니다. 명령줄은 위 영어 절에 그대로 있습니다.

디스크를 키우려면 이미지 파일을 truncate -s 16G 하면 됩니다. 파일은
sparse 라서 실제로 쓰는 만큼만 차지하고, 다음 부팅에 /data 가
알아서 늘어납니다.


SSH 로 들어가기
---------------
SSH 서버는 처음부터 들어 있고 자동으로 뜹니다. 비밀번호 인증은
아예 컴파일하지 않았습니다 — 인터넷에 물린 보드에서 비밀번호는
시간 문제라서 선택지로 두지 않았습니다.

전에는 그 때문에 갓 구운 카드에 아무도 들어갈 수 없었고, 키를 넣는
유일한 방법이 카드 리더였습니다. 이제는:

      authkey new

기기에서 키 쌍을 만들고, 공개키를 등록하고, 개인키를 가져갈 수 있는
자리에 두고, 이 기계의 실제 주소가 들어간 접속 명령줄을 그대로
출력합니다.

이미 쓰던 키를 넣고 싶으면, 카드의 첫 번째 파티션이 FAT32 라
어느 컴퓨터에서나 열립니다:

      cat ~/.ssh/id_ed25519.pub >> /media/BOOT/authorized_keys

/boot/authorized_keys 가 있는 동안은 그쪽이 원본이고, 기기 안의
사본을 고쳐도 부팅할 때 덮어씁니다. 기기에서 관리하려면 /boot 에서
그 파일을 지우세요. 이렇게 만든 이유는 /data 가 통째로 망가져도
카드만 뽑으면 키를 다시 넣을 수 있어야 하기 때문입니다.

주소는 `ifconfig` 나 `info net` 으로 확인합니다. 사용자는 root
하나입니다. 가상머신이면 포트를 넘겨서 localhost:2222 로 붙습니다.

안 될 때:

      authkey -l              지금 어떤 키가 허용돼 있나
      service status dropbear
      firewall status
      netstat -l              뭐가 듣고 있나
      logd                    /data/log/auth 의 로그인 기록


무엇을 할 수 있나
-----------------
      help                    모든 명령어, 묶어서
      help <이름>             그중 하나
      info                    이 기계에 대한 모든 것
      info -s                 짧은 판

  텍스트와 스크립트
      sed awk grep diff sort uniq cut tr printf xargs head tail wc
      nl rev cmp seq find tee cat more edit

      grep 은 POSIX 를 따릅니다 — + 와 ? 는 보통 문자이고, -E 로
      확장 문법, -F 로 그냥 문자열 검색입니다. grep, sed, awk 가
      엔진 하나를 같이 써서 셋에서 패턴의 뜻이 같습니다.

  셸
      파이프, 2> 와 2>&1 을 포함한 리디렉션, && 와 ||, if, while,
      for, break, continue, 함수, $(...) 와 백틱, 변수, 글로브,
      백그라운드 작업, read, shift, export.

      로그인할 때 프로필을 읽습니다 — /etc/profile 다음에
      ~/.profile. /root 는 데이터 파티션에 있으므로 ~/.profile 은
      재부팅을 넘겨 남습니다. 설정은 거기에 두시면 됩니다.

  저장장치
      disk part datadisk expandfs fsck storage automount dd df du

      USB 드라이브를 꽂으면 /media 아래에 알아서 붙습니다.
      재부팅을 넘겨 같은 자리에 두려면 입양시키세요:
          storage adopt /dev/sdb 사진
      입양한 드라이브는 장치 이름이 아니라 파일시스템 레이블로
      찾으므로 다른 포트에 꽂아도 같은 자리에 옵니다.

  네트워크와 서비스
      net dhcp ifconfig route ping nslookup wget netstat firewall
      httpd wpa_supplicant

      httpd 는 디렉터리를 HTTP 로 서비스합니다. 기본으로 켜져 있지
      않습니다 — 모든 보드에서 웹서버가 도는 건 아무도 원한 기본값이
      아닙니다:
          service add httpd -d /data/www -p 8080
          firewall allow 8080
      `service add` 를 하면 init 이 지킵니다. 죽으면 다시 뜨고,
      재부팅해도 남고, 메모리가 모자라도 guard 가 죽이지 않습니다.

      포트 여는 데 더는 카드 리더가 필요 없습니다:
          firewall allow 8080     firewall deny 8080
          firewall ports          뭐가 열려 있고 왜 열렸나

  패키지
      pkg     이 시스템을 위해 만든 작은 패키지들, /data 로 바로
      apt     진짜 데비안 패키지, /data/debian 아래 별도 트리로.
              처음 한 번은 95MB 를 받아 440MB 로 풉니다. 그래서
              이미지에 넣지 않았습니다. 거기 설치한 어떤 것도 이
              시스템의 명령어를 망가뜨릴 수 없습니다 — 거기에 들어
              있지 않으니까요. rm -rf /data/debian 하면 전부
              되돌아갑니다.
          apt install ripgrep
          apt run rg --version

  파이썬
      CPython 3.12 와 pip, 그리고 옆에 glibc 가 있어서 C 확장이
      들어간 휠도 됩니다. 일반 리눅스 바이너리도 그 glibc 위에서
      `run` 을 붙이든 안 붙이든 돕니다.

  안 죽게 하는 것들
      guard watchdog bootcount service integrity defend logd top ps

      guard 가 메모리, 온도, 전압, CPU, 디스크를 봅니다. 포크
      폭탄은 한 번의 패스로 정리됩니다. 메모리 고갈에서는 원인이
      된 프로세스를 죽이고 init, 셸, SSH, 워치독은 절대 건드리지
      않습니다. init 은 서비스 목록에 있는 것을 다시 살리고, 5분을
      못 버틴 부팅이 다섯 번 이어지면 /data/rc.local 을 건너뛰어
      나쁜 스크립트가 사람을 가두지 못하게 합니다.


재부팅을 넘겨 무엇이 남나
-------------------------
      /data                       남습니다
      /root                       남습니다 (실체가 /data/root)
      /bin /lib /usr /opt /sbin   남습니다 (/data 오버레이).
                                  cp mytool /bin/ 이 내일도 있습니다
      /mnt/<입양한 드라이브>      남습니다, 레이블로 다시 찾습니다
      /media/<자동 마운트>        임시입니다, 빼면 사라집니다
      /etc /tmp /var              사라집니다, 일부러

/etc 가 매 부팅마다 커널 이미지에서 다시 만들어지는 이유는
/etc/rc 와 /etc/services 가 /data 를 마운트하기도 전에 읽히기
때문입니다. 그 둘의 낡은 사본이 시스템 업데이트를 가리면 보드가 안
뜹니다. 개별 파일은 남길 수 있습니다:

      persist etc keep /etc/hosts
      persist etc                 지금 뭐가 남고 있나


직접 빌드하기
-------------
필요한 패키지와 명령줄은 위 영어 절에 그대로 있습니다. arm64 는
x86 호스트에서 크로스 빌드하고, amd64 는 네이티브입니다. 세 배포본을
한 번에 만들려면:

      ./tools/mkdist.sh

체크섬과 다운로드 페이지는 이 스크립트가 실제 파일에서 만들어냅니다.
손으로 적으면 누군가 다시 빌드하고 잊는 순간 어긋나고, 맞지 않는
체크섬은 없는 것보다 나쁩니다 — 받는 사람이 전송 실패인지 문서가
낡은 건지 구별할 수 없으니까요.

mkrootfs 는 소스보다 오래된 바이너리가 들어간 이미지를 만들기를
거부합니다. 실제로 한 번 그렇게 나갔습니다 — 파일을 고치고 한쪽
아키텍처만 빌드했더니, 이미 맞는 코드를 두고 셀프테스트가
실패했습니다.


빌드 확인하기
-------------
      ./tests/selftest.sh

기기 안에서 돌립니다. 모든 검사가 PASS, FAIL, SKIP 으로 시작하는
한 줄을 찍으므로, 이 시스템을 전혀 모르는 무언가가 시리얼 로그에서
결과를 읽어낼 수 있습니다. SKIP 은 여기서는 그 검사를 할 수 없다는
뜻이고 이유를 말합니다 — "가상머신에는 워치독이 없다"는 시험
기계에 대한 사실이지 결함이 아닙니다.

형식적인 절차가 아닙니다. 위 "믿고 쓰기 전에"에 적힌 결함 대부분이
"이건 되겠지" 하고 검사를 추가했다가 안 되는 것을 발견한 경우입니다.


소스는 어디에
-------------
      userland/       두 아키텍처가 함께 쓰는 소스 한 벌
        libc/         자체 libc, 시스템 콜 위에 직접
        <이름>/       명령어 하나에 디렉터리 하나
      firmware/       베어메탈 부트로더
      kernel/         커널 설정과 빌드 스크립트
      boot/           부트 파티션에 들어가는 것들
      tools/          이미지 생성, 서명, 다운로드 페이지
      tests/          셀프테스트
      GUIDE/          이 파일과 BRANCHES.txt
      dist/           완성된 이미지

arm64/ 나 amd64/ 폴더는 없습니다. 두 아키텍처가 같은 소스를 쓰기
때문입니다. 실제로 다른 것은 셋뿐입니다 — 시스템 콜 번호, crt0.S 의
진입점, 커널 설정. 복사해서 나눠두면 한쪽만 고치는 사고가 나고,
여기서 실제로 두 번 겪었습니다.
